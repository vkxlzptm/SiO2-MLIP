## S1-5 OMP 스레드 스케일링 (2026-08-10)

`in.timing_probe` (= `in.timing_nano`의 run 20 → run 3), mpirun 없이 직접 실행, 두 번째 `run 3` 기준.
i5-11600K = 물리 6코어 / 12논리스레드.

| OMP | Loop (3 step) | s/step | atom-step/s | CPU use | speedup |
|---|---|---|---|---|---|
| 1 | 24.3006 | 8.100 | 266.7 | **60.0 %** | 1.00 |
| 4 | 13.5215 | 4.507 | 479.2 | 291.9 % | 1.797 |
| 6 | 13.2641 | 4.421 | 488.5 | 441.0 % | 1.832 |
| 12 | 13.2502 | 4.417 | 489.1 | 447.6 % | 1.834 |

**결론 3가지**

1. **하이퍼스레딩(12)은 이득 없음.** 6 대비 0.1 % (노이즈 수준). STATUS 규칙 3(랭크×스레드 ≤ 6) 유지.
2. **스레드 병렬화 자체가 거의 안 먹는다.** 1→6이 **1.83배뿐**이고 4에서 이미 포화(4→6 = +1.9 %).
   CPU 441 %를 쓰면서 wall은 1.83배 → CPU-초당 유효 일은 41 %. 나머지는 OpenMP 배리어 스핀으로 추정.
   원인 추정: 7net-nano는 채널 32 / 3층으로 텐서가 작아 스레드 분할 이득 < 동기화 오버헤드.
   (논문이 GPU 벤치만 제시한 것과 정합. 단 이건 우리 추론이지 논문이 말한 바 아님.)
3. **OMP=1의 CPU 60 %는 설명 안 됨.** 단일 스레드인데 40 %가 idle.
   메모리 지연 바운드일 가능성이 높지만 확인 안 함. 운용 결론에는 영향 없어 추적 중단.

**파생 가설 — "리플리카 병렬이 스레드보다 3.3배 효율적" → S1-7에서 반증됨 (실제 1.12배)**

가설: OMP=1 프로세스를 6개 동시에 돌리면 266.7 × 6 = 1,600 atom-step/s (3.28배).
**틀렸다.** 가설이 전제한 "동시 실행해도 개당 속도가 유지된다"가 성립하지 않는다. → S1-7 참조.
당시 리스크로 (b) 메모리 대역폭 경합을 적어두긴 했으나, 헤드라인 숫자는 그게 없다는 가정 위에 세운 것.

## S1-6 cutoff 변종 스윕 (2026-08-10, `in.sweep`)

동일 구조·동일 조건(`neighbor 1.0`, OMP=6, mpirun 없음)에 포텐셜만 교체.
E/atom·maxF는 위치만의 함수라 속도와 무관 → 단일점 값 그대로.
Press는 `velocity create 300`이 걸린 timing 구간 값이므로 운동에너지 항을 뺐다:
P_kin = (N−1)k_B·300/V = 2159 × 8.617333e−5 × 300 / 27554.315 Å³ = **3,245.4 bar**.
(검산: 5.5의 93,915.0 − 3,245.4 = 90,669.6 = 앞서 직접 측정한 순수 virial과 **완전 일치**. 뺄셈 신뢰 가능.)

| 모델 | r_c (Å) | FullNghs | edge/atom | E/atom (eV) | maxF (eV/Å) | **P_virial (GPa)** | **s/step** | atom-step/s | vs 5.5 |
|---|---|---|---|---|---|---|---|---|---|
| 7net-nano-4.5 | 4.5 | 118,972 | 55.08 | −7.7348588 | 5.7713 | **9.230** | **2.401** | 899.5 | **1.84×** |
| 7net-nano-5.0 | 5.0 | 151,268 | 70.03 | −7.7423925 | 5.7467 | **9.353** | 3.314 | 651.9 | 1.33× |
| 7net-nano-5.5 | 5.5 | 190,870 | 88.37 | −7.7388532 | 5.5738 | **9.067** | 4.418 | 489.0 | 1.00× |
| 7net-nano-6.0 | 6.0 | 239,548 | 110.90 | −7.7381505 | 5.7472 | **9.668** | 5.623 | 384.2 | 0.79× |

### 결과 1 — 압축 상태 결론은 cutoff에 robust

P_virial 9.067 ~ 9.668 GPa, 평균 9.33, 산포 **±3.2 %**.
E/atom 산포는 **7.5 meV/atom**. → "BKS의 ρ=2.607 구조를 SevenNet은 ~9 GPa 압축 상태로 본다"는
S1 핵심 결론은 모델 선택에 좌우되지 않는다. **S2 결론이 흔들릴 위험 제거됨.**

### 결과 2 — 비용은 r_c³ 에 1 % 이내로 비례

`s/step ∝ r_c³` (skin 포함 이웃리스트 크기가 아니라 **모델 실제 edge 수**를 따라감):

| r_c | (r_c/4.5)³ 예측 | 실측 s/step | 오차 |
|---|---|---|---|
| 5.0 | 3.294 | 3.314 | +0.6 % |
| 5.5 | 4.384 | 4.418 | +0.8 % |
| 6.0 | 5.692 | 5.623 | −1.2 % |

→ **비용 모델 확보**: 2160원자 기준 `s/step = 0.02635 × r_c³` (이 머신, OMP=6).
S2/S3 예산을 임의 cutoff에 대해 계산 가능.
논문이 지목한 "neighbor list construction" 요인은 우리 조건(2160원자, 재빌드 0)에선 안 보이고,
순수 edge 수 효과만 남았다. 논문 GPU 벤치의 배수를 가져다 쓰면 안 되는 이유.

### 해석 주의 — 이건 수렴 계열이 아니다

E/atom·maxF·P 모두 **r_c에 단조적이지 않다**(5.5가 maxF 최소, 6.0이 P 최대).
네 모델은 하나를 정밀화한 게 아니라 **각각 독립적으로 2 epoch 학습된 별개 체크포인트**다.
따라서 cutoff 간 차이는 "긴 cutoff가 더 정확하다"가 아니라 **독립 학습의 산포**로 읽어야 한다.
6.0의 9.67 GPa를 "가장 수렴한 값"으로 해석하면 안 됨.

## S1-7 리플리카 동시 실행 실측 (2026-08-10) — **가설 반증**

`in.sweep` + `deployed_nano_4.5.pt`, 각 프로세스 OMP=1, n개 동시. 두 번째 `run 3` 기준, n개 평균.

| n | 개당 s/step | 개당 감속 | 총 atom-step/s | OMP=6 단일 대비 | 시스템 RAM used |
|---|---|---|---|---|---|
| 1 | 4.241 | 1.00× | 509 | 0.57× | 3,134 MB |
| 2 | 5.367 | 1.27× | 805 | 0.89× | 5,335 MB |
| 4 | 8.997 | 2.12× | 960 | 1.07× | 6,704 MB |
| 6 | 12.868 | **3.03×** | **1,007** | **1.12×** | **13,392 MB (여유 2,005)** |

*(비교 기준 OMP=6 단일 실행 = 2.401 s/step = 899.5 atom-step/s)*

**결론: 리플리카 병렬은 이득이 거의 없다 (1.12배). 예측 3.28배는 틀렸다.**
원인은 개당 속도가 n=6에서 **3.03배 느려지는 것**. 앞서 리스크로 적어둔 메모리 대역폭 경합이
실제로 지배적이었다. n=2는 오히려 OMP=6 단일보다 **느리다**(0.89배).

**RAM 한계**: 프로세스당 약 2.1 GB. n=6에서 available이 2 GB까지 떨어짐 → **6이 하드 상한.**

### 이 세 측정(S1-5, S1-7)을 관통하는 하나의 설명

세 가지 이상 징후가 전부 같은 원인을 가리킨다:
- OMP=1인데 CPU 사용률 60 % (연산 바운드면 100 %여야 함)
- 스레드 1→6이 1.83배에서 포화, HT는 0
- 프로세스 6개 동시 실행 시 개당 3.03배 감속

→ **7net-nano의 CPU 추론은 연산 바운드가 아니라 메모리 바운드다.**
채널 32 / 3층이라 산술 강도(arithmetic intensity)가 낮아, 코어를 늘리든 프로세스를 늘리든
메모리 대역폭이라는 같은 벽에 부딪힌다.
**이 머신의 천장은 약 1,000 atom-step/s이고, 병렬화 전략으로는 못 넘는다.**
(GPU가 필요한 이유. 논문이 GPU 벤치만 제시한 것과도 정합 — 단 이 해석은 우리 추론이지 논문 주장 아님.)

### 운용 결정

**S2·S3 전부 OMP=6 단일 실행으로 간다.** 리플리카는 1.12배를 위해 운용 복잡도와 RAM 위험을
떠안을 값어치가 없다. 자연스럽게 독립적인 작업 묶음(예: E–V 곡선의 여러 부피점)이 생기면
그때만 6개 동시 실행을 쓰되, **기대 이득은 3배가 아니라 10 % 남짓임을 전제로 설계할 것.**

## 미측정 / 열린 항목

- 순수 LJ(쿨롱·kspace 없음) 속도는 **측정하지 않았음**. BKS의 kspace 비중(19.3 %)으로 볼 때 LJ가 더 빠를 것은 분명하나 배수는 추정하지 않는다. 필요하면 별도 5초 벤치로 실측할 것.
- 2랭크 크래시의 정확한 지점(백트레이스) 미확보. 운용상 불필요하므로 추적 안 함.
- **cutoff 변종 미측정.** `7net-nano-4.5 / 5.0 / 5.5 / 6.0` 존재 확인(`sevenn/util.py` L292–299).
  로컬에는 5.5만 번들, 나머지는 첫 호출 시 자동 다운로드됨(4.5 다운로드 성공 확인, 458 KB).
  논문 권고: "accuracy exhibits **weak dependence on r_c**", 5.5가 robust default, 효율이 필요하면 4.5.
  **단 논문의 속도 이득은 우리에게 그대로 오지 않는다** — 논문은 cutoff 간 비용 차이를
  "primarily from **neighbor list construction** ... increasingly impacts performance as system size grows"
  로 귀속시켰는데, 논문 벤치는 GPU·최대 7만 원자이고 우리는 CPU·2160원자에 `Neighbor list builds = 0`이다.
  우리 쪽 이득은 edge 수 감소(r³: 5.5→4.5 = 0.55배)에서만 나오므로 1.8배보다 작을 것. **배수는 실측 전 추정 금지.**
- 리플리카 동시 실행의 RAM·대역폭 한계 미측정 (위 S1-5 파생 결론 참조).
